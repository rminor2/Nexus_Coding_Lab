1. Context and Requirements
For this assignment, I focused on the CustomerLifecycleService.deactivate function in the Nexus2 project. Originally, when a customer was deactivated, the system sent out an event containing their email and the reason for deactivation. The notification system also included that reason in the message sent to the customer. The November 10 requirements changed this because the reason could contain private information that shouldn't be shared publicly .
The system still needed to follow its original rules. Admins and managers can deactivate accounts, but viewers cannot. The customer must exist, and the reason must contain at least five characters after removing extra spaces. If any of these checks fail, the system shouldn't change anything, send notifications, or create an audit record. A successful deactivation should return the customer with active=False.
The new requirements also stated that public events could contain the customer's ID and email, but not the private reason. Notifications must say exactly "Your Atlas account has been deactivated." The system also needs to save one internal audit record containing the customer ID, the person who deactivated the account, and the cleaned-up reason. Even if a notification fails, the audit record must already be saved, and the customer must remain inactive .
On November 12, another requirement was added to save audit records to a local file. A new instance of the audit store must be able to read previous records, and adding new records cannot overwrite older ones. The assignment assumes one writer and successful file operations, so handling crashes, multiple writers, and encryption isn't required .
My recommendation is to keep auditing separate from the main service and use FileAuditStore to save records. We also kept InMemoryAuditStore for existing tests. I reviewed the changes from the team's merged commit 8f2fdae and verified the results discussed below .

2. Proposed Design
The main change was separating private audit information from public events. Instead of sending the reason through the event system, the lifecycle service saves it directly to a private audit store. The public event only contains the information needed for notifications.
Each part of the system has its own responsibility. AuthorizationService checks permissions, the repository finds and saves customers, and CustomerLifecycleService handles the deactivation process. AuditStore provides a way to save records, while FileAuditStore handles writing and reading them. EventBus sends events, and the notification subscriber sends the customer message.
The lifecycle service saves records using record_deactivation(customer_id, actor_id, reason). It only calls this method after checking permissions, finding the customer, and validating the reason. FileAuditStore then adds a JSON record to the file using append mode, which keeps older records from being overwritten.
Records can be read through FileAuditStore(path).records. If the file doesn't exist, the system returns an empty list. Other file errors are allowed to raise exceptions. The audit interface only handles writing, so reading still depends on the file store. Access to these files is controlled by operating-system permissions rather than a separate application permission system [3].
For example, if a manager deactivates an account with the reason " Duplicate account ", the system first checks their permissions and confirms that the customer exists. It removes the extra spaces, changes the customer's status to inactive, and saves the customer. Next, it writes the customer ID, manager's ID, and "Duplicate account" to the audit file. Finally, it publishes the public event without the reason and sends the generic notification.
This keeps private information out of public events while still allowing the company to keep a record of what happened.

3. Other Designs Considered
I considered two other ways to handle the audit records.
Alternative A: Have the lifecycle service write directly to the file.
This would be simpler because we wouldn't need a separate audit component. However, it would also mean the lifecycle service handles customer accounts, file storage, and events. If we wanted to change how records were stored later, we'd have to modify the same code that handles deactivations.
I prefer keeping auditing separate because it makes the code easier to organize, test, and update. The downside is having another interface and some extra setup.
Alternative B: Create a separate private event system.
Another option would be to send the audit information through a second event system that only internal components could access. A private subscriber would save the record before the public event was sent.
This would work as long as the record was saved exactly once and before the public event. It could also support more internal subscribers later. However, it would require another event system and additional rules to make sure everything happens in the correct order.
I prefer calling the audit component directly because it's simpler for this assignment. We only need one audit operation, so a second event system seems unnecessary. Both alternatives would still need file storage to meet the November 12 requirements.

4. Tradeoffs and Testing
There are two main tradeoffs with the design we chose.
The first is keeping auditing separate. This makes it easier to change storage methods without rewriting the lifecycle service. It also makes testing more straightforward. The downside is having another component to maintain, and the current interface doesn't provide a shared method for reading records.
The second is saving the audit record before publishing the public event. This is important because a notification failure won't erase the record. However, the customer is already saved as inactive before the audit happens. If writing the audit fails, the customer could remain inactive without a new record. Since the assignment assumes successful audit writes, we didn't add a rollback system or transactions.
We ran several tests to make sure everything worked correctly.
test_03_reason_is_retained_in_internal_audit checks that a manager can deactivate a customer and that the audit file contains the correct customer ID, actor ID, and trimmed reason. Along with test_01, test_02, and test_04, it also helps verify that public events don't expose private reasons, notifications use the correct message, and customers are returned as inactive.
We also ran test_08_notification_failure_does_not_erase_audit, which deliberately makes the notification system fail with a RuntimeError. The test passed, confirming that the customer stays inactive, the audit record remains saved, the private reason stays out of the public event, and the error is still raised.
Two additional tests checked specific requirements. test_09 verified that " abcde " is accepted as a valid reason and saved without extra spaces. test_10 saved a record, created a new file store using the same path, added another record, and confirmed that both records could still be read. Each contract test used a separate temporary directory to prevent interference.

5. Response to Architecture Reviews
Omar Hassan's Security Architecture Review discusses the importance of limiting access to information and making sure components only receive the data they need [4]. This supports our decision to remove the deactivation reason from public events entirely.
Simply hiding the reason in the notification message wouldn't be enough because other subscribers could still access it. Removing it from the event itself is safer. However, the audit file still stores reasons as plain text, and we haven't added encryption or application-level access controls.
Carlos Rivera's Testability Architecture Review focuses on separating responsibilities and making system behavior easier to verify [5]. Our design follows this idea by allowing us to test the audit component separately from notifications. The lab adapter reads actual stored records, and test_10 checks persistence using new store instances instead of reusing the same list.
These reviews also show an important tradeoff. We need access to audit records for testing, but we don't want private information to be available to everyone. For this assignment, we used temporary files, fake test reasons, and internal checks. This makes testing possible without putting private information into public events, although file permissions would still need more attention in a real system.

6. Final Recommendation
I recommend keeping the separate audit component and using FileAuditStore for this project. It meets the current requirements, keeps private information separate from public events, and makes the code easier to test and maintain.
The tests show that the main functionality works, but one additional check would be useful. I would run two separate Python processes, with the first saving an audit record and closing completely. The second would open the same file and verify that the record was still there. This would provide stronger evidence of persistence, although it wouldn't test crash recovery.
If this system were used in production, I would also consider a database with transactions and stricter access controls, especially if multiple processes needed to write records. Handling missing files, damaged records, failed writes, and record retention would also need more work.
Overall, I think this design is a good solution for the assignment because it meets the requirements without making the system more complicated than necessary.
